# Операционный runbook: vibe-order-infra

Действия оператора для вероятных эксплуатационных событий на production
VPS. Архитектура и обоснование решений — README.md; процедуры деплоя/
обновления — [DEPLOYMENT.md](DEPLOYMENT.md). Команды предполагают, что вы
находитесь в корне репозитория на VPS, с валидным `.env`.

Прежде чем выполнять любую команду, помеченную **[ОПАСНО]** — прочитайте
предупреждение целиком. Ни одна такая команда не должна выполняться "на
автомате" без подтверждённого свежего backup.

## Совместимость backup ↔ версия приложения ↔ ревизия схемы

Это правило нужно понимать до того, как вы окажетесь в ситуации, где
восстановление уже необходимо — см. разделы "Backup"/"Restore" ниже.

- Каждый backup сделан при какой-то конкретной ревизии Alembic
  (`alembic_version` в самом дампе).
- Backend-код на старте **отказывает** запускаться (readiness = `503`,
  контейнер помечается `unhealthy`), если подключенная схема **новее или
  иначе устроена**, чем ожидает текущая версия кода. Конкретно проверяется
  (`app/core/schema_check.py::ensure_database_ready`): (а) отсутствие любой
  из ожидаемых таблиц; (б) для каждой ОЖИДАЕМОЙ таблицы — точное совпадение
  колонок/типов/nullable/PK/важных constraints, причём незнакомая
  (лишняя) колонка НА ЭТОЙ таблице тоже считается несовпадением, не только
  отсутствующая. Это фиксированный список конкретных таблиц/колонок, а не
  полный Alembic-diff: совершенно посторонняя таблица, которую это
  приложение вообще не ожидает (не входит в проверяемый список), сама по
  себе этой проверкой **не отклоняется** — в отличие от
  `app/db_admin/adopt_legacy.py`'s legacy-фингерпринта (одноразовая
  проверка при усыновлении БД, см. DEPLOYMENT.md), который как раз
  отклоняет любую лишнюю таблицу целиком. Это специально: молча работать с
  рассинхронизированной (в пределах того, что вообще проверяется) схемой
  опаснее, чем не запуститься вовсе.
- Отсюда правило: **backup, восстановленный под backend-код версии X,
  безопасен, только если ревизия Alembic в backup'е ≤ ревизии, которую
  ожидает код X.** Если backup старее — после restore обязательно
  `alembic upgrade head` (см. "Restore" ниже, это уже часть процедуры).
  Если backup **новее** текущего задеплоенного кода (например, откатили
  backend, а восстановили backup, сделанный уже после более новой
  миграции) — сначала обновите backend до версии, которая знает эту
  ревизию, **до** старта; в этом репозитории нет проверенных
  `downgrade()`-путей ни для одной миграции (см. `backend/alembic/versions/`)
  — откат схемы назад не поддерживается инструментарием репозитория.

## Backend не стартует

Симптомы: `docker compose ps` показывает `backend` в `Restarting`/
`unhealthy`, HTTPS отдаёт 502/503 от Nginx.

```bash
docker compose ps
docker compose logs --tail=200 backend
```

Наиболее вероятные причины, по частоте:

1. **Схема не мигрирована** (см. "Migration failure" и правило совместимости
   выше) — лог содержит `DatabaseNotMigratedError`. Не пытайтесь чинить
   вручную SQL-ом — примените миграцию (`docker compose up -d --no-build
   db-roles-finalize`, см. DEPLOYMENT.md), затем пересоздайте backend.
2. **`JWT_SECRET_KEY` отсутствует/placeholder** — `docker compose up`
   откажется стартовать backend вообще (`${JWT_SECRET_KEY:?...}` в
   `docker-compose.yml`) или `Settings` отклонит его при старте процесса.
   Проверьте `.env` (см. DEPLOYMENT.md, "Секреты").
3. **PostgreSQL ещё не готова** (холодный старт/ребут VPS) — `depends_on:
   condition: service_healthy` должен был это предотвратить; если всё же
   произошло, смотрите следующий раздел.
4. **Ресурсы** — см. "Нехватка диска/ресурсов" ниже.

Никогда не увеличивайте `restart`-политику или не убирайте healthcheck,
чтобы "заставить" контейнер выглядеть работающим — это скрывает, а не
чинит проблему.

## Readiness не проходит (`/api/ready` = 503)

`/api/ready` не публикуется наружу — проверяется изнутри:

```bash
docker compose exec backend python healthcheck.py; echo "exit: $?"
docker compose exec backend python -c \
  "from app.core.database import engine; from app.core.schema_check import ensure_database_ready; ensure_database_ready(engine)"
```

Второй команда напечатает точную причину (`DatabaseNotMigratedError` с
конкретным списком: какие из ОЖИДАЕМЫХ таблиц отсутствуют и/или на каких
из них разошлись колонки/constraints/FK — включая как отсутствующие, так
и лишние неожиданные колонки НА ЭТИХ таблицах; посторонняя таблица, которую
приложение вообще не ожидает, в этот список не попадает, см. правило
совместимости в начале документа), если readiness падает из-за схемы — это
тот же самый read-only check, что и сам эндпоинт. Если она проходит без
ошибок, а `/api/ready` всё равно `503` —
проблема временная (сетевая/connection pool) или PostgreSQL стала
недоступна уже после старта — см. следующий раздел.

## PostgreSQL недоступна

```bash
docker compose ps postgres
docker compose logs --tail=200 postgres
docker compose exec postgres pg_isready -U "$POSTGRES_USER" -d "$POSTGRES_DB"
```

- Если контейнер `Exited`/`Restarting` — смотрите его логи на предмет
  disk full (см. "Нехватка диска" ниже) или повреждения данных на volume
  `postgres-data`.
- Если контейнер `healthy`, а backend всё равно не может подключиться —
  проверьте, что `APP_DB_USER` действительно существует и активна
  (`docker compose up -d --no-build db-roles-finalize` идемпотентно
  пересоздаёт/подтверждает роль).
- **Не удаляйте volume `postgres-data`** как способ "починить" недоступную
  БД — это необратимая потеря данных. Если PostgreSQL не поднимается из-за
  повреждения данных на диске — это сценарий restore из backup, см. ниже,
  не пересоздание volume с нуля.

## Migration failure (`alembic upgrade head` упал)

```bash
docker compose logs --tail=200 db-migrate
docker compose ps --all db-migrate   # код выхода != 0 - без --all one-shot контейнер не
                                      # покажется в выводе вообще (не Exited, а просто отсутствие)
```

`db-migrate` не перезапускается автоматически (one-shot, `restart` не
задан) — `backend` не запустится следом, т.к. `db-roles-finalize` (и
значит `backend`) зависит от успешного завершения `db-migrate`
(`condition: service_completed_successfully`). Это правильное поведение,
не баг: лучше остановленный деплой, чем backend поверх частично
применённой миграции.

1. Прочитайте ошибку в логе `db-migrate` — почти всегда это либо
   конфликт данных (миграция добавляет `NOT NULL`/constraint, которому
   существующие строки не удовлетворяют), либо сетевая проблема до
   PostgreSQL.
2. **Не** запускайте `alembic upgrade head` вручную с runtime
   (`APP_DB_USER`) креденшлом — у него нет прав DDL, он гарантированно
   упадёт с permission denied, это не альтернативный путь.
3. Если проблема в данных — почините данные (миграционным скриптом или
   вручную, от имени `MIGRATION_DB_USER`) и повторите
   `docker compose up -d --no-build db-roles-finalize`. Alembic хранит
   версию транзакционно — миграция, упавшая на середине, не оставляет
   `alembic_version` продвинутой на неприменённую ревизию.
4. Если миграция сама по себе ошибочна — откатите деплой backend-кода до
   версии без этой миграции (см. "Rollback деплоя" ниже) и чините
   миграцию как обычный баг в новом коммите, не патчите её задним числом
   на production.

## Rollback деплоя

Актуально после обновления `backend`, когда **схема не менялась** в этом
релизе (см. предупреждение ниже, если менялась):

```bash
# Откат тега, установленного во время предыдущего деплоя (см. DEPLOYMENT.md,
# "Обновление / перезапуск" - шаг с "docker tag ... rollback-<дата>").
docker tag vibe-order-infra-backend:rollback-<дата> vibe-order-infra-backend:latest
docker compose up -d --no-build --no-deps backend
docker compose ps backend
curl -fsS http://127.0.0.1/api/health   # или через HTTPS снаружи
```

**Если релиз, который вы откатываете, менял схему БД** — откат ОДНОГО
backend-образа не откатывает схему автоматически (Alembic не поддерживает
проверенный `downgrade()` ни для одной ревизии в этом репозитории, см.
"Совместимость backup" выше). Более старый backend-код будет ожидать более
старую схему и откажется стартовать против уже мигрированной новой — в
этом случае откат состояния возможен только через restore БД из backup,
сделанного **до** проблемного релиза (см. "Restore" ниже), с
соответствующей потерей всех данных, записанных после этого backup. Именно
поэтому backup перед схема-меняющим релизом — обязательный шаг, а не
рекомендация (см. README, "Ограничение: развертывание базы данных").

## Обновление образа приложения

Полная процедура — DEPLOYMENT.md, "Обновление / перезапуск (production)".
Коротко: собрать/запушить новый образ → backup (если меняется схема) →
применить миграции (`db-roles-finalize`, тянет за собой bootstrap+migrate)
→ пересоздать `backend` → smoke-check.

## Backup PostgreSQL

```bash
backup_dir="$HOME/vibe-order-infra-backups"
install -d -m 700 "$backup_dir"

backup_file="$backup_dir/backup-$(date +%Y%m%d-%H%M%S).sql"

# --clean --if-exists: дамп содержит DROP ... IF EXISTS перед каждым
# CREATE - нужно для restore-модели ниже ("Restore PostgreSQL": восстановление
# в заведомо чистую пересозданную базу, см. этот раздел). Без --clean обычный
# psql-restore падает на "relation already exists" на любой непустой базе.
#
# Оба условия обязательны, ни одно не заменяет другое: "pg_dump exit 0" и
# "$backup_file непустой" - shell-редирект ">" создаёт (обнуляет)
# $backup_file ДО того, как pg_dump вообще запустится, поэтому pg_dump,
# упавший НЕ сразу (разрыв соединения с postgres, диск переполнился,
# statement_timeout, OOM-killer), уже успевает записать часть дампа и
# оставляет непустой, но обрезанный/невалидный файл - проверка только
# "test -s" приняла бы такой файл как валидный backup. Проверка только кода
# возврата, в свою очередь, не поймала бы pg_dump, отработавший с exit 0, но
# по какой-то причине не написавший ничего.
#
# ВАЖНО - безопасность под "set -e": статус завершения команды, служащей
# условием "if", НЕ триггерит errexit (это стандартное исключение shell,
# не специфика этого скрипта) - в отличие от прежней формы "cmd; status=$?",
# где сам "set -e" оборвал бы выполнение на строке с pg_dump ДО того, как
# успеет отработать "status=$?", и карантин ниже вообще не запустился бы,
# оставив обрезанный файл под нормальным именем backup'а. Эта форма
# безопасна независимо от того, активен ли "set -e" в вызывающем скрипте -
# проверено эмпирически (успешный дамп; pg_dump, упавший с ненулевым
# кодом; то же самое под "set -e") в рамках этого исправления. Никакого
# "|| true" в этой цепочке - падение здесь обязано реально останавливать
# процедуру.
if docker compose exec -T postgres sh -c \
     'pg_dump --clean --if-exists -U "$POSTGRES_USER" "$POSTGRES_DB"' \
     > "$backup_file"
then
  if [ -s "$backup_file" ]; then
    ls -lh "$backup_file"
  else
    echo "backup FAILED (pg_dump exited 0 but wrote no data) - do not proceed" >&2
    # Карантин, а не тихое удаление - неполный файл остаётся на диске под
    # заведомо непутающим именем (для post-mortem), но никогда не будет
    # принят ни этой, ни какой-либо другой процедурой как валидный backup
    # ("*.incomplete" не совпадает ни с одним wildcard/шаблоном, который
    # процедура restore ниже когда-либо использует для выбора файла).
    mv "$backup_file" "$backup_file.incomplete" 2>/dev/null || rm -f "$backup_file"
    exit 1
  fi
else
  dump_status=$?
  echo "backup FAILED (pg_dump exit=$dump_status) - do not proceed" >&2
  mv "$backup_file" "$backup_file.incomplete" 2>/dev/null || rm -f "$backup_file"
  exit 1
fi
```

`$backup_file` — единственная переменная, указывающая на только что
созданный файл; `$backup_dir` вне рабочей копии репозитория, права `700`
(внутри — потенциально чувствительные данные заявок). См. также README,
"Ограничение: развертывание базы данных" — та же процедура, тот же
стоп-критерий (код возврата `pg_dump` **и** `test -s`, не одно из двух).

Запишите (например, рядом с файлом backup'а) версию backend-образа/git SHA
на момент backup'а — она понадобится при restore, см. правило
совместимости выше.

## Restore PostgreSQL

**[ОПАСНО] Безвозвратно уничтожает ВСЁ текущее содержимое `$POSTGRES_DB`
целиком** (не только строки/таблицы, которые есть и в backup'е — сама база
пересоздаётся с нуля, см. шаг 2 и обоснование ниже). Не выполнять без
явного решения оператора и, где возможно, свежего backup'а текущего (пусть
даже проблемного) состояния перед восстановлением поверх него — на случай,
если решение восстанавливать было ошибочным.

**Почему не просто "restore поверх текущей БД".** Раньше эта процедура
восстанавливала `pg_dump --clean --if-exists` прямо поверх уже
существующей `$POSTGRES_DB`, полагаясь на то, что `--clean --if-exists`
сам всё почистит. Это не так: `--clean --if-exists` эмитирует `DROP ...
IF EXISTS` только для объектов, которые есть в самом дампе — то есть
были в источнике на момент backup'а. Он ничего не знает и ничего не
может сделать с объектом, которого в дампе нет: вручную добавленной
таблицей/колонкой/индексом, остатком предыдущего инцидента, дрифтом от
частично применённой миграции — restore пройдёт "успешно" (exit 0), а
такой объект переживёт его нетронутым. Эмпирически подтверждено —
`backend/tests/test_restore_roundtrip.py::test_clean_if_exists_restore_does_not_remove_target_only_drift`
воспроизводит именно это на предварительно "задрифтованной" базе. Поэтому
восстанавливаем не поверх текущей БД, а в заведомо чистую, только что
пересозданную — тогда дрифту физически негде спрятаться.

**Как выбрать нужный файл backup'а.** `$backup_dir` (`$HOME/vibe-order-infra-backups`)
может содержать несколько файлов — выбирайте конкретный файл по имени
(содержит дату/время создания и, если использовалась форма имени из README,
`<release-tag>`), а не "последний по времени" через wildcard/`ls -t | head
-1`: это тот самый принцип "без wildcard", которого держится сама backup-
процедура (см. "Backup PostgreSQL" выше). Файлы с суффиксом `.incomplete`
(см. "Backup PostgreSQL" выше — так карантинится неудавшийся/пустой дамп)
никогда не являются валидным backup'ом и не выбираются для restore ни при
каких обстоятельствах — точный выбор файла по имени, а не по маске/паттерну,
уже сам по себе исключает случайное совпадение с ними. Сверьтесь с версией backend-
образа/git SHA, записанной рядом с файлом при его создании (см. "Backup
PostgreSQL" выше) — она определяет, какой ревизии Alembic ожидать внутри
дампа (см. "Совместимость backup ↔ версия приложения ↔ ревизия схемы" в
начале этого документа) и какую версию backend'а разворачивать вместе с
этим restore.

```bash
# 1. Остановить backend - он не должен обслуживать трафик поверх БД,
#    которая вот-вот будет уничтожена и пересоздана. Если запущен профиль
#    admin - также docker compose stop pgadmin (иначе его открытое
#    соединение может помешать DROP DATABASE на шаге 2).
docker compose stop backend

# 2. Пересоздать целевую базу с нуля - это и есть "верифицированно чистая
#    цель": WITH (FORCE) обрывает любые оставшиеся соединения с базой,
#    поэтому DROP не блокируется и не зависит от того, что все клиенты
#    уже отключились сами. После этого шага в базе гарантированно нет
#    вообще ничего - ни ожидаемых таблиц, ни дрифта, ни объектов от
#    предыдущих инцидентов.
docker compose exec -T postgres sh -c \
  'psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d postgres -c \
     "DROP DATABASE IF EXISTS \"$POSTGRES_DB\" WITH (FORCE)"'
docker compose exec -T postgres sh -c \
  'psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d postgres -c \
     "CREATE DATABASE \"$POSTGRES_DB\""'

# 3. Восстановить выбранный $backup_file в эту заведомо пустую базу. Роли
#    (MIGRATION_DB_USER/APP_DB_USER) уже существуют в кластере (создавались
#    один раз при bootstrap - роли не привязаны к конкретной базе данных,
#    DROP DATABASE их не затрагивает) - дамп из "pg_dump --clean" содержит
#    собственные ALTER TABLE ... OWNER TO/GRANT операторы, ссылающиеся на
#    эти же имена ролей, поэтому ownership и права восстанавливаются как
#    часть самого restore, без отдельного adopt_legacy (adopt_legacy -
#    только для ДОмиграционных дампов без alembic_version, см.
#    DEPLOYMENT.md). "--clean --if-exists" в самом дампе здесь становится
#    no-op'ом (DROP ... IF EXISTS на объект, которого и так нет), не мешает.
docker compose exec -T postgres sh -c \
  'psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"' \
  < "$backup_file"

# 4. Актуализировать роли/права и, если backup старее текущего кода,
#    догнать схему до head (см. "Совместимость backup" выше). Безопасно и
#    идемпотентно выполнять всегда.
docker compose up -d --no-build db-roles-finalize
docker compose ps --all   # bootstrap/migrate/finalize - Exited (0)

# 5. Поднять backend и проверить readiness.
docker compose up -d --no-build --no-deps backend
docker compose exec backend python healthcheck.py && echo "backend ready"

# 6. Функциональная проверка данных (примеры счётчиков - сверить с
#    ожидаемым состоянием на момент backup'а, см. "как выбрать нужный
#    файл" выше).
docker compose exec -T postgres sh -c \
  'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "SELECT count(*) FROM applications;"'
```

`ON_ERROR_STOP=1` останавливает соответствующий шаг на первой же
SQL-ошибке вместо того, чтобы молча продолжить с частично выполненной
операцией — если шаг 2 или 3 завершился с ошибкой, не переходите к
следующему шагу: разберитесь в причине (несовместимый дамп, недостаточно
прав, база всё ещё занята активными соединениями) прежде чем продолжать.

Восстановление на **другой, чистый сервер** (не тот кластер, где ролей ещё
нет) требует сначала `docker compose run --rm db-roles-bootstrap`, иначе
шаг 3 упадёт на `ALTER TABLE ... OWNER TO <роль>`, ссылаясь на ещё не
существующую роль.

## Проверка backup (backup verification)

Backup, который ни разу не восстанавливали, нельзя считать рабочим.
Периодически (и обязательно после любого изменения схемы) проверяйте
восстановимость на **одноразовой, отдельной** базе — никогда на
production:

```bash
docker compose exec -T postgres sh -c \
  'createdb -U "$POSTGRES_USER" restore_verify_test'
docker compose exec -T postgres sh -c \
  'psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d restore_verify_test' \
  < "$backup_file"
docker compose exec -T postgres sh -c \
  'psql -U "$POSTGRES_USER" -d restore_verify_test -c "SELECT count(*) FROM applications;"'
docker compose exec -T postgres sh -c \
  'dropdb -U "$POSTGRES_USER" restore_verify_test'
```

Имя `restore_verify_test` содержит `test` намеренно — то же соглашение,
которого держится тестовый набор проекта (см.
`backend/tests/db_safety_guard.py`), хотя эта конкретная проверка выполняется
вручную, не через pytest.

## Ротация секретов

**`JWT_SECRET_KEY`.** Ротация делает недействительными **все** выданные
токены — все залогиненные администраторы получат `401` и должны будут
войти заново; это ожидаемо, не баг.

```bash
# Сгенерировать новый секрет, обновить .env (JWT_SECRET_KEY=...), затем:
docker compose up -d --no-build --no-deps backend
```

**`MIGRATION_DB_PASSWORD`/`APP_DB_PASSWORD`** (миграционная и runtime-роли).
Обновите `.env`, затем пересоздайте пароль самой роли в PostgreSQL
(`bootstrap_roles.py` при повторном запуске выставляет пароль роли из
текущего значения переменной окружения — `ALTER ROLE ... PASSWORD`, см.
`app/db_admin/bootstrap_roles.py::_ensure_role`) и только потом
перезапустите сервисы, которые этой ролью пользуются:

```bash
docker compose up -d --no-build db-roles-finalize   # применяет новые пароли ролей в PostgreSQL
docker compose up -d --no-build --no-deps backend    # backend переподключается с новым APP_DB_PASSWORD
```

Это работает, потому что `db-roles-finalize` сам подключается как
кластерный admin (`POSTGRES_USER`/`POSTGRES_PASSWORD`) и **от его имени**
выполняет `ALTER ROLE` над миграционной/runtime ролями — то есть требует,
чтобы `POSTGRES_PASSWORD` в `.env` уже был ТЕКУЩИМ (действующим) значением
на момент запуска. Если вы ротируете и `POSTGRES_PASSWORD` тоже — сначала
пройдите процедуру ниже целиком (включая обновление `.env`), и только
потом запускайте `db-roles-finalize`.

**`POSTGRES_PASSWORD`** (кластерный суперпользователь — тот, что создаёт
сам официальный образ `postgres` при **первой** инициализации кластера).
**Простая замена значения в `.env` и `docker compose up -d postgres`
пароль в PostgreSQL НЕ меняет** — `POSTGRES_PASSWORD` образ `postgres`
читает только при первичной инициализации ещё пустого data-каталога
(`initdb`); на уже существующем volume (`postgres-data`) он попросту
игнорируется при каждом следующем старте контейнера, а реальный пароль
роли остаётся тем, что был установлен раньше и хранится в самом кластере
(`pg_authid`). `bootstrap_roles.py`/`db-roles-bootstrap`/`db-roles-finalize`
тоже не помогут: они управляют только `MIGRATION_DB_USER`/`APP_DB_USER` (см.
модуль `app/db_admin/bootstrap_roles.py`), не кластерным admin'ом (см.
[docs/DEPLOYMENT.md](DEPLOYMENT.md), "Конфигурация и переменные окружения").
Реальная ротация — двухфазная: **сначала** меняем сам пароль в PostgreSQL,
аутентифицировавшись СТАРЫМ (ещё действующим) credential'ом, **потом**
обновляем `.env`, чтобы будущие запуски знали новое значение.

```bash
# Фаза 1: сменить пароль в PostgreSQL, используя ещё действующий СТАРЫЙ
# POSTGRES_PASSWORD из текущего .env (в этом шаге .env пока НЕ меняем).
#
# ВАЖНО - "-h postgres" здесь обязателен, не опционален. Без него
# "docker compose exec postgres psql ..." подключается через Unix-сокет
# внутри контейнера, а официальный образ postgres по умолчанию оставляет
# ОБЕ строки "local" (сокет) И "host ... 127.0.0.1/32" (loopback) на
# "trust" в pg_hba.conf - это значит, что и голый socket-путь, И "-h
# 127.0.0.1" аутентифицируют ЛЮБОЙ пароль (включая заведомо неверный) без
# проверки вообще, независимо от значения PGPASSWORD. Реально проверяет
# пароль только catch-all правило "host all all all scram-sha-256" в
# конце pg_hba.conf - оно применяется, когда подключение приходит НЕ с
# 127.0.0.1/::1, то есть через собственный сетевой алиас сервиса Compose
# ("postgres" на app-net - тот же путь, которым уже подключаются backend
# и db-roles-bootstrap/finalize). Эмпирически подтверждено на
# одноразовом disposable-контейнере с тем же образом (см. этот файл в
# истории коммитов): "-h 127.0.0.1" и голый socket-путь принимают
# заведомо неверный PGPASSWORD (exit 0); "-h postgres" корректно
# отклоняет его ("password authentication failed", exit != 0) и
# принимает верный.
#
# Подключаемся интерактивно и меняем пароль через "\password" - psql сам
# спросит новое значение дважды, со скрытым вводом, и сформирует
# корректно экранированный ALTER ROLE сам; так новый пароль никогда не
# попадает в аргументы команды/историю шелла/логи.
set -a; source .env; set +a   # экспортирует СТАРЫЙ POSTGRES_USER/POSTGRES_PASSWORD в этот шелл, не печатает их
docker compose exec -e PGPASSWORD="$POSTGRES_PASSWORD" postgres \
  psql -h postgres -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"
# на приглашении psql:
#   \password
#   (ввести новый пароль дважды)
#   \q
```

**Проверка Фазы 1 (что процедура действительно требует текущий пароль).**
Перед сменой пароля (или на отдельной disposable БД с тем же образом)
убедитесь, что путь реально проверяет пароль, а не просто "проходит":

```bash
# Заведомо неверный пароль через "-h postgres" - ожидается отказ
# аутентификации, ненулевой exit code:
docker compose exec -e PGPASSWORD="obviously-wrong-password" postgres \
  psql -h postgres -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "SELECT 1"; echo "exit: $?"
# ожидаемо: "password authentication failed for user ...", exit 2

# Тот же заведомо неверный пароль ЧЕРЕЗ Unix-сокет (без "-h") -
# демонстрация известного ограничения дефолтного pg_hba.conf: НЕ
# использовать этот путь для ротации, он ничего не доказывает про знание
# пароля:
docker compose exec -e PGPASSWORD="obviously-wrong-password" postgres \
  psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "SELECT 1"; echo "exit: $?"
# известно: подключается успешно (exit 0) несмотря на неверный пароль -
# именно поэтому Фаза 1 выше обязательно использует "-h postgres", а не
# голый socket-путь
```

```bash
# Фаза 2: только ПОСЛЕ успешной Фазы 1 - обновить .env тем же новым
# значением, что было только что введено в \password, и, если заодно
# ротируете MIGRATION_DB_PASSWORD/APP_DB_PASSWORD - обновить их тоже
# (см. блок выше), затем одной командой применить всё через
# db-roles-finalize (теперь аутентифицируется НОВЫМ POSTGRES_PASSWORD) и
# пересоздать backend, если менялся APP_DB_PASSWORD:
docker compose up -d --no-build db-roles-finalize
docker compose ps --all   # bootstrap/migrate/finalize - Exited (0)
docker compose up -d --no-build --no-deps backend
```

**Проверка.** `docker compose exec backend python healthcheck.py && echo
"backend ready"` — backend успешно подключился новым `APP_DB_PASSWORD`.
Для самого `POSTGRES_PASSWORD`: `docker compose ps --all` — все four
backend/DB-lifecycle сервиса `Exited (0)`/`healthy`, без `Restarting`
(признак не проходящей аутентификации).

**Откат/восстановление, если новое значение оказалось неверным.** Если
Фаза 1 (`\password`) прошла успешно, но в `.env` на Фазе 2 попал не тот
текст (опечатка) — реальный пароль в PostgreSQL остаётся тем, что был
введён в `\password`, просто `.env` теперь ему не соответствует: исправьте
`.env` на то же значение (либо, если оно утеряно, подключитесь так же, как
в Фазе 1, ещё раз действующим на данный момент паролем и повторно
выполните `\password`, установив заведомо известное значение) — заново
проходить всю процедуру с нуля не требуется. Если сама Фаза 1 не
выполнялась и вы уже перезаписали `.env` "будущим" значением, которое
никогда не применялось к PostgreSQL — просто верните в `.env` прежний
(всё ещё действующий) пароль и начните процедуру заново; ничего в
PostgreSQL при этом повреждено не было (Фаза 1 не выполнялась, ничего не
менялось).

**`PGADMIN_DEFAULT_*`/Registry htpasswd** — см. README ("pgAdmin",
"Docker Registry"/`registry/create-user.sh`) — вне зоны ответственности
Alembic/ролевой модели backend'а.

## Recovery администратора

- Забытый пароль администратора — восстановления "по email" не существует
  (нет email-сервиса в этом проекте). Единственный путь — прямое
  вмешательство оператора в БД (сброс `password_hash` через SQL от имени
  `MIGRATION_DB_USER` **или** удаление строки в `admins` и повторный
  `bootstrap-admin`, если это единственный администратор).
- **Полная потеря доступа** (например, единственный администратор удалён
  по ошибке) — если `admins` пуста, `python -m app.cli bootstrap-admin`
  создаёт нового первого администратора тем же безопасным путём, что и
  при первом деплое (см. DEPLOYMENT.md, "Первый администратор"). Если
  `admins` **не** пуста, но пароль неизвестен — bootstrap откажет
  ("администратор уже существует"); нужен прямой SQL-сброс
  `password_hash`, как в пункте выше.

## Безопасное выключение / перезапуск

```bash
# Плановый перезапуск одного сервиса без простоя остальных:
docker compose restart backend

# Полная плановая остановка стека (например, перед maintenance окном):
docker compose stop

# Возврат после остановки - НЕ "up -d" с нуля (это пересоздало бы
# контейнеры и заново прогнало бы one-shot DB-lifecycle сервисы, что
# безопасно, но не нужно для простого возврата после stop):
docker compose start
```

`docker compose down` удаляет контейнеры (не volumes, если не передан
`-v`) — не используется в рамках обычного цикла обновления/перезапуска
(см. README, "Порядок деплоя"); допустим только для полного
демонтирования стека, осознанно.
